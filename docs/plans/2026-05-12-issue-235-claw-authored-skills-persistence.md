# Issue #235 — Persist claw-authored skills separately from pod-declared skills

Status: draft (Claude). Awaiting adversarial review from codex.

## Problem

`claw up` materializes everything into `.claw-runtime/<service>/`. On the next `claw up`, that directory is staged as `.previous-<ns>` and replaced with a fresh tree, then the previous staging is removed on commit. Anything an agent wrote into its runner skill directory inside `.claw-runtime` is therefore destroyed on the next apply.

The motivating case is a Hermes runner that authored a skill under `/root/.hermes/skills/` at runtime. Without a durable mount under that path, the next pod regeneration silently loses it.

Self-authored skills are runtime state of the *claw*, not pod configuration. They must survive `claw up`, image rebuilds, container recreation, and (where possible) driver migration. Pod-declared skills must remain operator-owned: read-only, regenerated by `claw up`, never clobbered by a misbehaving claw.

## Existing scaffolding the fix can lean on

The codebase already has the right primitives. We do not need new abstractions, only a new mount.

- `MaterializeResult.SkillDir` (`internal/driver/types.go:208`) — every driver already declares its container skill path. The seven runner drivers map to:
  - `openclaw`, `nullclaw`: `/claw/skills`
  - `microclaw`: `/claw-data/skills`
  - `hermes`: `/root/.hermes/skills`
  - `nanobot`: `/root/.nanobot/workspace/skills`
  - `picoclaw`: `<picoclawWorkspaceDir>/skills`
  - `nanoclaw`: `/workspace/container/skills`
- `MaterializeOpts.StateDir` (`internal/driver/types.go:195`) — already wired to a durable per-service host directory: `memoryRoot/<service>` where `memoryRoot = .claw-memory`. This is the "writable state survives `claw up`" path.
- Pod-declared skills are already mounted as individual files (`cmd/claw/compose_up.go:756-770`):
  ```go
  for _, sk := range rc.Skills {
      containerPath := filepath.Join(result.SkillDir, sk.Name)
      if result.SkillLayout == "directory" {
          stem := strings.TrimSuffix(sk.Name, filepath.Ext(sk.Name))
          containerPath = filepath.Join(result.SkillDir, stem, "SKILL.md")
      }
      result.Mounts = append(result.Mounts, driver.Mount{
          HostPath: sk.HostPath, ContainerPath: containerPath, ReadOnly: true,
      })
  }
  ```
  Each declared skill becomes its own read-only bind mount at a specific path under `SkillDir`.
- `ensurePersistentCllamaDir` (`cmd/claw/compose_up.go:4857`) — the helper for "make a 0o777 dir at `podDir/<name>` that survives `claw up`". Already used for `.claw-memory`, `.claw-auth`, `.claw-session-history`.

The fix slots in cleanly: introduce one more persistent dir, mount it writable at `SkillDir`, keep the existing per-file read-only mounts as overlays.

## Design

### Durable host path

Per claw (per base service), the durable skills root is:

```
<podDir>/.claw-state/<service>/skills/
```

Created with permissions `0o777` to match the foreign-UID pattern the rest of the codebase already uses for writable state (`ensurePersistentCllamaDir`, `PreparePortableMemory`).

`<service>` is the **base service name** from the pod, not the ordinal compose service. This mirrors the existing `.claw-memory/<service>/memory/` shape, which is also keyed per base service (`StateDir = filepath.Join(memoryRoot, name)` in `compose_up.go:739`). Phase 1 carries this asymmetry forward: with `count > 1`, ordinals share both memory and self-authored skills. Per-ordinal isolation for both is a separate issue; trying to fix it only for skills would create a confusing split.

**Why `.claw-state/` and not extending `.claw-memory/`?**

- "Memory" is one kind of durable claw state. Skills are another. Naming them under a single tree is conceptually cleaner.
- A future rename of `.claw-memory/<svc>/memory/` -> `.claw-state/<svc>/memory/` is a separate, larger migration (touches portable-memory repair, manifest schemas, and existing pods). Introducing `.claw-state/` now creates the right home for that future move without forcing it.
- Alternative considered: `.claw-memory/<service>/skills/`. Reuses an existing root but bakes in the naming asymmetry. Rejected on aesthetics; flagged for codex to challenge.

The new top-level dir is added to the docs list of claw-owned runtime state alongside `.claw-runtime`, `.claw-memory`, `.claw-auth`, `.claw-session-history`, `.claw-memory-tombstones`. (Yes, that yard is already wide; consolidating it is out of scope here.)

### Compose mount shape

For each managed claw with a non-empty `SkillDir`, `claw up` emits:

1. **Writable base mount** (rw bind):
   `<podDir>/.claw-state/<service>/skills/ : <SkillDir> : rw`
2. **Read-only declared-skill overlays** (existing, unchanged):
   `<sk.HostPath> : <SkillDir>/<name> : ro` (or `/<stem>/SKILL.md` for `SkillLayout == "directory"`)

Mount order in `volumes:` is **writable first, read-only overlays after**. Docker's bind-mount precedence is by container path (each mount is its own mount point), so order does not change runtime semantics — but emitting writable-then-overlay matches the conceptual layering and makes generated compose files easier to read.

`SkillDir == ""` (no skills concept for this driver — currently no driver, but possible for future drivers) emits neither mount.

### Path-conflict semantics

If a pod-declared skill names a file that the claw also created at the same container path, the read-only declared mount wins (it is layered on top of the writable parent). On a fresh apply with no claw-authored content yet, the claw sees only the declared skills as files inside its skill dir. The claw can create *new* files at *new* paths under the dir, and those persist.

A claw cannot delete or overwrite a declared skill because the per-file mount is read-only. This is the desired operator-authority guarantee.

### Persistence path validation

The `<service>` token is the pod service name from `claw-pod.yml`. We must reject anything that would let a malicious or buggy pod escape the durable root:

- Reject empty or whitespace-only service names (already enforced upstream by pod parsing — verify, do not duplicate).
- Reject service names containing `/`, `\`, `..`, or NUL.
- Reject service names that, after `filepath.Clean`, are not equal to themselves (catches `./foo`, `foo/.`, etc.).
- Verify that the resulting cleaned path stays under `<podDir>/.claw-state/` (defense-in-depth `filepath.Rel` check).

Centralize this in one helper, e.g. `validateClawStateService(name string) error` in `cmd/claw/compose_up.go` or `internal/driver/shared/`. Reuse for any future `.claw-state/<service>/...` introductions.

The pod parser already constrains service names to a tighter regex; this is belt-and-braces in case a future code path produces an unvalidated name.

### Driver migration

The issue mentions "driver migration where possible". Driver migration today means changing `CLAW_TYPE` between deploys (e.g. openclaw → hermes). Because the durable skills dir is keyed by **service name**, not driver, a `CLAW_TYPE` change preserves the dir's contents. But:

- The container path may change (e.g. openclaw `/claw/skills` → hermes `/root/.hermes/skills`). The bind target moves; the host content is unchanged.
- Skill file format conventions may differ (`SkillLayout == "directory"` for Claude Code-style runners). A skill authored by a hermes claw at `trading/ticker-discovery/SKILL.md` may not be findable by an openclaw runner that expects flat files. This is a runtime-format problem, not a persistence problem; we surface it in docs and do not auto-translate.

No driver code changes are required for migration. The host dir is driver-agnostic.

### Initial seeding and empty-state behavior

On first `claw up` for a service, `<podDir>/.claw-state/<service>/skills/` is created empty (0o777). The container sees an empty writable directory at its `SkillDir`, with declared-skill files overlaid as read-only. This is the same shape that exists today on every `claw up` — no behavior change for pods without self-authored skills.

We do **not** seed any file. Drivers that need a `SKILL.md` (e.g. Claude Code directory layout) already handle that via declared skill mounts; self-authored content lives alongside, not instead of.

### Per-claw vs per-ordinal: explicit acknowledgement

For `count > 1` services, all ordinals of the same base service share `.claw-state/<service>/skills/`. This matches the existing `.claw-memory/<service>/memory/` precedent. Two implications:

- Two ordinals of the same base service can race when writing the same path. We do not solve this here. Same as memory today.
- A future change that introduces per-ordinal state isolation (for both memory and skills) is the right place to address this. Out of scope for #235.

Document this clearly in the new docs section.

### Generated artifact behavior

- `compose.generated.yml` shows two `volumes:` entries per claw: `.claw-state/<svc>/skills/:<SkillDir>:rw` and the existing per-file overlays.
- `claw down` does not delete `.claw-state/` — it's durable state, parallel to `.claw-memory`.
- `claw doctor` and `claw inspect` do not need new logic; they already surface mounts from the generated compose.

Implementation will be confined to:

  - Introduce `claw-state` constant or reuse `ensurePersistentCllamaDir(podDir, ".claw-state")`.

  - In the materialize loop, after declaring pod-skill mounts, prepend (or append; order is cosmetic) the writable base mount when `result.SkillDir != ""`.
  - Add `validateClawStateService(name)` and call it before forming the host path.
- `internal/driver/shared/` *(optional)*
  - If the helper has reuse potential, move it to `shared`. Otherwise keep it local to `cmd/claw`.
- Docs:
  - `MANIFESTO.md` or a new doc page describing the pod-skills vs claw-skills distinction.
  - `README.md` or a guide page: how to discover the durable host path; that `claw down` does not clear it.
  - `CLAUDE.md` "Repo-Specific Gotchas" section: one bullet noting `.claw-state/` is durable, parallel to `.claw-memory`, and shared across ordinals.

No driver code changes. No `MaterializeResult` schema change. No `MaterializeOpts` change. The compose-emission layer owns the new mount because that's where all other host-path decisions live.

## Tests

All in `cmd/claw/compose_up_test.go` and `internal/pod/compose_emit_test.go`.

1. **Writable base mount emitted per managed claw with SkillDir.**
   Build a fixture pod with one nullclaw service, no declared skills. Assert generated compose contains `.claw-state/<service>/skills:<container-path>:rw` and that the host dir exists post-`claw up` (or test pass-2 path directly).
2. **Mount ordering: writable base before read-only overlays.**
   Pod with one service, one declared skill. Assert the writable base mount appears in the `volumes:` list at a lower index than the declared-skill file mount. This is cosmetic but is part of the acceptance criteria.
3. **Declared skill at same path wins.**
   Pod with one service, one declared skill named `trading.md`. Pre-create `.claw-state/<service>/skills/trading.md` with sentinel content. Assert the declared skill's `HostPath:.../trading.md:ro` mount is emitted; the writable base still binds the dir. (Runtime layering is Docker's responsibility; the test asserts compose shape, not container behavior.)
4. **Service name validation.**
   Direct unit tests on `validateClawStateService`: reject `..`, `foo/bar`, `\x00bar`, `./foo`, empty string. Accept normal pod service names.
5. **`SkillLayout: directory` (Claude Code) still produces correct overlay paths.**
   Existing test should cover this; verify the writable base mount sits underneath the `<stem>/SKILL.md` overlay.
6. **`SkillDir == ""` emits no writable base mount.**
   Synthesize a `MaterializeResult` with empty `SkillDir` (no current driver does this; use a test-only stub) and assert no `.claw-state` mount is emitted.
7. **`count > 1` ordinals share the same writable base mount.**
   Pod with `count: 2`. Assert each ordinal compose service has the same `.claw-state/<base-svc>/skills/` host path mapped to its respective container path.
8. **Persistence across `claw up`.**
   Integration-tagged test: run `claw up`, write a file into `.claw-state/<svc>/skills/foo.md` on the host, run `claw up` again, assert the file is still present (the dir is not under `.claw-runtime` and is not rotated).
9. **Persistence across image rebuild / container recreation.**
   Same as 8 but exercise `claw build` between the two `claw up` calls. The host file must still exist.

Spike test impact: `TestSpikeRollCall` and `TestSpikeComposeUp` should not change behavior, but verify they still pass.

## Open questions for codex

1. **`.claw-state/` vs `.claw-memory/<svc>/skills/`** — should we accept the asymmetry and reuse `.claw-memory`, or introduce a new top-level durable root? My read is that `.claw-state/` is cleaner long-term; codex should pressure-test that.
2. **Per-ordinal vs per-base sharing for `count > 1`** — is "share across ordinals" the right Phase 1 behavior, mirroring memory? Or do self-authored skills need per-ordinal isolation now because the issue's motivating example was a single-ordinal pod and the failure mode for shared ordinals is silent corruption?
3. **Mount-order order** — Docker is documented as "last writer wins" for overlapping bind mounts at the *same* target, but here each overlay is at a *different* target (a file under a dir), so order should not matter. Confirm there is no edge case I'm missing (e.g. macOS Docker Desktop, podman).
4. **Path-validation centralization** — put the helper in `internal/driver/shared/` for future reuse, or keep it local to `cmd/claw/compose_up.go`? My instinct says local until there's a second consumer.
5. **Promotion of self-authored skills into pod source** — the issue mentions promoting one runtime-authored skill into pod source as an example. Is that a repo update for this PR, or strictly downstream? My read is that this PR ships the platform fix; the example pod promotion is a downstream commit.

## Out of scope

- Renaming `.claw-memory/` → `.claw-state/<svc>/memory/`.
- Per-ordinal isolation for memory or skills.
- A `claw skills` subcommand for inspecting / promoting self-authored skills into pod source.
- Auto-format translation between flat and directory skill layouts on driver migration.
- An MCP tool for letting an agent introspect its own skills dir.
