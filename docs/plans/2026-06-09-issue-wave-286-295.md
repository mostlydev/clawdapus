## cllama commit B — #287 + #288

### #287 pre-dispatch inputSchema validation

Insertion: `executeManagedOpenAITool` / `executeManagedAnthropicTool` (`internal/proxy/toolmediation.go:894,957`), after the `call.ParseErr` check, before `dispatchManagedTool`. To be precise about wording: the upstream LLM round that emitted the call already happened; what validation skips is the **providing-service dispatch** (the HTTP/MCP call to the tool's service).

- Validator: hand-rolled JSON Schema subset, no new dependency — `required`, `properties` (recursive), primitive `type` (object/string/number/integer/boolean/array/null), `enum`, `items`. Fail-open on unsupported/malformed schema constructs (non-object schema, unknown type values, `$ref`, `allOf` etc.) — validation must never block a call the provider would accept; explicit tests for fail-open cases.
- Violation result shape (defined, so audit behavior is defined): synthetic tool result via `toolErrorPayload("schema_validation", <message with JSON paths>, 0, <violations details>)`. Enters `tool_trace` like any tool error → surfaces as `TOOL_ERR` in `claw audit`. No provider `error` event is emitted (no upstream/service call happened).
- Wrong-location hint: when a missing required property's name exists elsewhere in the submitted args (nested), the message names both paths ("required property \"target_price\" missing at top level; found at proposal_context.target_price").
- Intervention: `managed_tool_schema_rejected:<canonical-tool>` via `LogIntervention`, byte-bounded message. Audit shows it under INT.
- Kill switch: `CLLAMA_TOOL_SCHEMA_VALIDATION=off` disables (default on). Bad validation logic can strand agents faster than provider 4xxs; the switch is the emergency rollback that doesn't need an image rollback.
- Rejected rounds still count against `max_rounds` (they consume an inference round).

### #288 presented-name rework

Current: `managedToolPresentedName(tool)` hashes any non-provider-safe name per-tool (`toolnames.go:23-51`); presentation sites are `buildOpenAIToolSchemas`/`buildAnthropicToolSchemas` (`handler.go:1120-1145`), `rewriteManagedAnthropicToolChoice` (`handler.go:1102-1118`), and `decorateManagedToolResult` (`toolmediation.go:1157`); resolution + hashless alias recovery in `resolveManagedTool` (`toolnames.go:90-133`) logs one intervention per call.

Change — per-manifest presentation map, not a local function tweak:

1. `buildManagedToolNameTable(tools []ToolManifestEntry)` computes presented names manifest-wide: provider-safe canonical → as-is; otherwise sanitized hashless form **if unique** across the manifest's sanitized forms and not colliding with any canonical; otherwise today's hashed form. Threaded through all presentation sites and resolution.
2. Resolution accepts, in order: canonical, current presented, **legacy hashed form** (for session-history replays and cross-turn continuity recorded under the old scheme), hashless alias. Ambiguity stays a hard miss (existing semantics in `toolnames_test.go` preserved).
3. Intervention demotion: hashless-alias recovery logs `managed_tool_hashless_alias` only on first occurrence per (agent, canonical tool) per process lifetime; subsequent recoveries are silent. With hash-free presentation the path only triggers for collision pods and stale histories anyway.
4. Tests: existing expectations in `toolmediation_test.go:197-313` (hashed result headers) updated consciously; new cases for collision pods, legacy-hashed resolution, `tool_choice` rewrite under both presentation modes, replay back-compat.
