# cllama Model Policy And Declared Fallbacks Plan

## Status

- Proposed on 2026-03-27.
- Motivating incident:
  - an OpenClaw runner selected provider `xai`
  - stripped the provider prefix from `xai/grok-4.1-fast`
  - sent bare `grok-4.1-fast` to `cllama`
  - `cllama` rejected the request because it currently trusts the runner's model string and requires `<provider>/<model>` on the OpenAI path
- There is also doc drift:
  - `cllama/README.md` lists "Per-agent model ACLs from metadata.json" as roadmap language
  - current code does not actually enforce model allowlists from agent context

## Goal

Move final model and provider choice into `cllama`, using compile-time policy generated by `claw up`.

In practical terms:

- pod config defines the allowed model set for each agent
- runners may suggest a model, but they do not have final authority
- `cllama` chooses the actual provider/model from the declared policy and live credential state
- automatic failover happens only within the declared set, never to an undeclared provider

## Why This Fits Clawdapus

This is the infrastructure-layer boundary Clawdapus is supposed to enforce.

- runners are untrusted workloads
- runner bugs should not bypass cost, geography, or provider policy
- prompt-induced self-switching should not unlock undeclared providers
- credential starvation already centralizes live provider capability in `cllama`
- `claw up` is already the compiler for feeds, auth, context, and runtime wiring

This means model policy belongs in compiled context plus `cllama`, not in prompts and not in runner-local state.

## Current State

### What Exists Today

- `Clawfile` model directives are parsed into `ResolvedClaw.Models`
- `claw up` materializes per-agent context under `.claw-runtime/context/<agent-id>/`
- `metadata.json` currently carries:
  - `service`
  - `pod`
  - `type`
  - `token`
  - `timezone`
- `cllama` loads that metadata but does not use it for model policy
- `cllama` trusts the incoming request's `model` field
- on the OpenAI path, `cllama` requires a provider-prefixed model string
- provider retry logic only rotates keys within the already selected provider

### What Does Not Exist Today

- no per-agent model allowlist in runtime context
- no clamped or rejected request behavior when a runner asks for a disallowed model
- no declared cross-provider fallback chain
- no policy intervention logging for model rewrites
- no compile-time representation of "allowed but not default" vs "eligible for automatic failover"

## Problem Statement

The current trust boundary is backwards.

Today:

- the runner chooses the model
- `cllama` mostly accepts that choice
- `cllama` only manages credentials for the chosen provider

That allows three classes of failures:

1. Runner bugs

- a runner strips a provider prefix
- a runner serializes the wrong slot
- a runner silently rewrites the model ID

2. Policy bypass

- a runner switches to a banned provider
- a runner upgrades itself to a more expensive model
- a runner leaks sensitive context to a provider that was never approved for that pod

3. Incomplete failover semantics

- `cllama` can only rotate keys inside one provider
- it cannot move from a declared primary to a declared fallback when the primary provider is exhausted

## Design Principles

1. Compile-time policy, runtime enforcement.
   `claw up` compiles per-agent model policy. `cllama` enforces it.

2. Runner requests are hints, not authority.
   A runner can request an allowed model, but it cannot expand its own policy.

3. Automatic failover must stay inside declared policy.
   No undeclared provider switching.

4. Default behavior should be resilient to runner bugs.
   Production default should clamp to an allowed model rather than fail hard on every mismatch.

5. Observability must show both requested and effective choices.
   Silent policy rewrites without telemetry will make incidents harder to debug.

## Proposed Semantics

### Policy Vocabulary

Each agent gets a compiled model policy with three concepts:

- `allowed`
  - every model the runner may explicitly request
- `failover`
  - the ordered chain `cllama` may automatically traverse when the chosen provider has no usable keys
  - this is derived from `allowed` slot ordering, not stored independently

### Recommended Defaults

- `allowed`:
  - all declared `MODEL` refs for the agent
  - preserve named slots so a runner can explicitly request another declared model if the pod author chose to expose one
- `failover`:
  - `primary`
  - followed by explicit fallback entries
  - do not automatically fail over into arbitrary named slots unless they are explicitly in the fallback chain

### Derived Fields

Do not store redundant `default` or `failover` arrays in `metadata.json`.

Instead:

- `default` is derived from the ordered `allowed` list:
  - `primary` if present
  - otherwise first allowed entry
- `failover` is derived at load time from the same ordered `allowed` list:
  - `primary`
  - then `fallback`
  - then remaining named slots in canonical order if later phases decide they are failover-eligible

This avoids consistency bugs between multiple stored views of the same policy.

### Request Handling Rules

On each request:

1. Read the runner-requested model.
2. Load the compiled model policy.
3. If policy is absent or `allowed` is empty:
   - skip policy enforcement
   - use current legacy behavior
4. Otherwise normalize the request against the compiled allowlist.
5. Determine the chosen requested target:
   - exact allowed full ref: use it
   - bare model that uniquely matches one allowed full ref: use the matching allowed ref
   - missing model: clamp to derived `default`
   - disallowed model: clamp to derived `default`
   - ambiguous bare model: clamp to derived `default`
6. Build the candidate execution list:
   - start with the chosen requested target
   - if that target is in the failover chain, append remaining failover entries after it
   - otherwise use only that target
7. For each candidate:
   - resolve the provider
   - try keys within that provider using current dead/cooldown logic
   - if a key is ready, dispatch
   - if all keys for that provider are dead or cooling down, continue to the next declared candidate
   - transport errors and upstream `5xx` responses do not trigger cross-provider failover
8. If no declared candidate is usable:
   - return an infrastructure error
   - do not escape the declared allowlist

## Default Enforcement Mode

Phase 1 should use `clamp`, not `reject`.

Meaning:

- disallowed or malformed runner model requests are rewritten to an allowed model
- the request still succeeds if an allowed model is usable
- `cllama` logs that a policy intervention happened

Why `clamp` first:

- runner bugs are expected
- production pods should keep operating while policy wins
- this directly fixes incidents like the stripped-prefix OpenClaw request

Future strict modes can be added later:

- `reject`
  - return `400` or `403` on disallowed models
- `audit`
  - allow but log

For managed pods, `clamp` should be the default.

## Format-Specific Behavior

### OpenAI Path

This is the main target for Phase 1.

- OpenClaw and several other runners use the OpenAI-compatible path
- full provider/model refs are natural here
- bare model requests can be normalized against the allowlist

This path must handle the stripped-prefix incident directly:

- runner sends `grok-4.1-fast`
- policy allowlist contains `xai/grok-4.1-fast`
- `cllama` maps it back to the allowed full ref

### Anthropic Path

Current Anthropic-path behavior in `cllama` is narrower:

- the path assumes the effective provider is `anthropic`
- there is no general Anthropic-path cross-provider bridge

Phase 1 should still apply model policy here, but with explicit limits:

- if the chosen effective model is anthropic-compatible, continue
- if the chosen effective model would require a provider/API-format bridge that does not exist on this path, fail clearly

This keeps the policy model coherent without pretending unsupported bridges already exist.

## Data Model

### Context Representation

Use `metadata.json` in Phase 1.

Reasons:

- the file already exists for every agent
- the README already points at metadata-based policy as the intended long-term direction
- no extra mount or loader is required

Add a new `model_policy` object:

```json
{
  "service": "weston",
  "pod": "trading-desk",
  "type": "openclaw",
  "token": "weston:secret",
  "timezone": "America/New_York",
  "model_policy": {
    "mode": "clamp",
    "allowed": [
      {
        "slot": "primary",
        "ref": "xai/grok-4.1-fast"
      }
    ]
  }
}
```

This single-entry example reflects the current Tiverton reality more closely: most live agent Clawfiles only declare `MODEL primary`.

### Why Not A Separate `model-policy.json` First

A separate file is reasonable later if policy grows beyond model enforcement.

For now, `metadata.json` is enough because:

- the data is small
- it is agent-local
- it is naturally loaded on every request
- it keeps the implementation focused on enforcement rather than file proliferation

## Compile-Time Changes

### `claw up`

Add model-policy compilation in `cmd/claw/compose_up.go` when building `cllama.AgentContextInput`.

Required steps:

1. Build an ordered view of declared model refs from `ResolvedClaw.Models`
2. Compute:
   - ordered `allowed`
   - implicit default from ordered `allowed`
   - implicit failover order from ordered `allowed`
3. Inject that structure into `Metadata`

### Canonical Ordering

Use deterministic ordering:

1. `primary`
2. `fallback`
3. remaining named slots sorted lexicographically

Automatic failover order should initially be:

1. `primary`
2. `fallback`

Other named slots should be allowed for explicit runner requests, but not automatically traversed unless the policy model is extended later.

### Empty Model Set

If `ResolvedClaw.Models` is empty:

- do not compile a `model_policy` block
- treat the agent as unconstrained from the policy layer
- leave runtime behavior unchanged

This keeps policy enforcement opt-in through existing `MODEL` directives.

### Helper Extraction

Add a helper in a new root-repo file such as `internal/cllama/modelpolicy.go` for turning `ResolvedClaw.Models` into compiled policy.

That avoids duplicating slot-ordering logic in:

- `compose_up.go`
- future inspection/debug output
- future docs or audit tooling

Do not overload `internal/cllama/context.go` tests with policy-shape logic. File I/O tests should stay there; policy compilation should have its own test file.

## cllama Runtime Changes

### Agent Context Loader

Extend `cllama/internal/agentctx` with parsed accessors for `model_policy`.

Suggested additions:

- typed `ModelPolicy`
- typed `AllowedModel`
- helper methods:
  - `DefaultModel()`
  - `AllowedModelRefs()`
  - `FailoverRefs()`
  - `HasPolicy()`

### Request Normalization

Before current provider resolution:

1. read requested model from the request body
2. consult the agent's compiled policy
3. if there is no policy, use current behavior
4. normalize the request to an allowed full ref

Normalization rules:

- exact match on full ref wins
- exact match on unique bare suffix wins
- unique match after provider normalization wins
- otherwise clamp to derived default

### Candidate Selection

After normalization:

1. build candidate refs from policy
2. try each candidate in order
3. for each candidate, try keys within that provider using the existing key-pool logic
4. stop at the first candidate whose provider has a usable key

This is the actual "transparent failover" story:

- it is not arbitrary provider substitution
- it is declared-model failover informed by live credential state

Implementation note:

- `dispatchWithRetry` cannot stay as a single-provider function if Phase 1 lands
- the runtime needs an outer loop over model candidates and an inner loop over keys within each candidate's provider
- "all keys in cooldown" for provider A must mean "advance to next declared candidate", not immediate failure for the whole request

### Dispatch Semantics

When a candidate is chosen:

- log `requested_model`
- log `effective_model`
- log `effective_provider`
- if the effective choice differs because of policy intervention, log that explicitly

Session history already records `RequestedModel`, `EffectiveProvider`, and `EffectiveModel` for successful calls. Reuse that shape and extend logs rather than inventing a second audit stream.

Implementation note:

- the current OpenAI path serializes `outBody` once, with `payload["model"]` already baked in
- that is fine for a single provider, but wrong for candidate failover
- once Phase 1 lands, the request body must be rebuilt per candidate model
- the easiest safe shape is:
  - keep the parsed payload map
  - clone or mutate it per candidate
  - serialize candidate-specific request bytes inside the candidate loop

## Observability

Add explicit intervention visibility.

Minimum requirement:

- structured log event when `cllama` rewrites a runner request because of policy

Suggested fields:

- `claw_id`
- `requested_model`
- `effective_model`
- `reason`
  - `missing`
  - `bare_model_normalized`
  - `disallowed_clamped`
  - `ambiguous_clamped`
  - `provider_exhausted_failover`

Nice-to-have follow-up:

- expose intervention counts in the `cllama` UI
- add policy interventions to `claw audit` normalization

## Compatibility Story

### Immediate Incident Coverage

This plan should fix the current stripped-prefix OpenClaw incident without any runner-specific special case:

- runner asks for bare `grok-4.1-fast`
- compiled policy knows the agent is only allowed `xai/grok-4.1-fast`
- `cllama` normalizes and dispatches to `xai`

### Runner Self-Switching

If a runner intentionally switches among declared models:

- allowed explicit request: honor it
- undeclared request: clamp to default

This gives pods room for controlled flexibility without giving runners policy authority.

### Expensive Or Banned Providers

If a runner tries:

- `openai/o3`
- `openrouter/gpt-5`
- any undeclared model/provider

`cllama` clamps or rejects based on policy mode.

### Deployment Assumption

No special migration-compatibility work is required for this project.

- there are only a small number of active installs
- root-repo and `cllama` changes can be deployed together
- mixed-version rolling compatibility is not a design goal for this plan

The implementation may still fall back safely when `model_policy` is absent, but rollout does not need to optimize for a long mismatch window.

## Non-Goals

- no free-form "best available model" routing across all configured providers
- no hidden substitution to undeclared providers
- no prompt-level policy logic
- no budget enforcement in this change
- no broad `cllama-policy` interception layer yet

## Implementation Phases

### Phase 0: Hotfix The Current Incident

Goal:

- make the current OpenClaw bare-model request succeed under declared policy

Scope:

- compile model policy into metadata
- normalize bare models against the allowlist on the OpenAI path
- clamp disallowed requests to default
- explicitly keep absent-policy behavior on the legacy path unchanged

This is the smallest safe step that fixes the production symptom and establishes the right trust boundary.

### Phase 1: Declared Automatic Failover

Goal:

- if the chosen provider has no usable keys, try the next declared fallback

Scope:

- add failover traversal across declared model refs
- keep retry semantics inside `cllama`
- preserve current provider-key cooldown/dead tracking
- do not trigger cross-provider failover on transport errors or upstream `5xx`

### Phase 2: Stricter Policy Surface

Goal:

- add explicit policy modes and stronger observability

Scope:

- configurable `clamp` vs `reject`
- intervention counters in UI/audit
- clearer user-facing error messages

## Rollout Plan

Because `cllama` is a submodule, this is a two-repo change.

Recommended sequence:

1. Write the ADR for the trust-boundary decision
2. Implement root-repo metadata generation
3. Implement `cllama` metadata loading and enforcement
4. Add unit tests in both repos
5. Run targeted tests:
   - root repo context tests
   - `cllama` proxy tests
6. Rebuild the local `claw` binary
7. Rebuild/pull the updated `cllama` image
8. Redeploy a real pod
9. Verify:
   - bare-model runner requests succeed only when policy allows them
   - undeclared model requests clamp or reject as expected
   - declared fallback works when the primary provider is exhausted

## Risks

1. Policy ordering mistakes

- if `allowed` or `failover` ordering is nondeterministic, agents may change behavior across deploys

2. Anthropic-path edge cases

- current bridging on the Anthropic path is narrower than on the OpenAI path

3. Silent intervention without telemetry

- if clamp behavior is not visible, debugging runner incidents becomes harder

4. Over-broad failover

- if implementation falls back across all allowed models instead of the declared failover chain, policy becomes too permissive

5. Candidate serialization mistakes

- if candidate-specific request bodies are not rebuilt, failover will dispatch the wrong upstream model

## Open Questions

1. Should `clamp` remain the default permanently for managed pods, or only as a rollout default?
2. Should explicit named slots beyond `fallback` be eligible for automatic failover, or only for explicit runner requests?
3. Should intervention events be a new structured log type, or encoded into the existing `intervention` field on request/response events?
4. Should phase 1 preserve the runner's raw requested model in history, or store the normalized requested full ref after allowlist resolution?
5. Should absent policy remain a permanent legacy mode for standalone `cllama`, or only a transitional convenience?

## Recommendation

Implement Phase 0 and Phase 1 together.

Reason:

- the production symptom is already showing why runner-selected models are not a safe authority surface
- Phase 0 alone fixes the current xAI/OpenClaw mismatch
- Phase 1 is the missing half of the architecture, because credential starvation only becomes truly useful when `cllama` can move across declared fallbacks instead of only rotating keys inside one provider

The end state should be simple:

- pod author declares the allowed model policy
- runners can request within that policy
- `cllama` enforces the boundary and chooses the live provider/model inside it
